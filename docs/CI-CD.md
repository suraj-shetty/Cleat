# CI/CD for Cleat

Concrete plan for building, signing, notarising and releasing this project from
GitHub Actions. Written against the repo as it stands: XcodeGen project
definition, Swift 6 strict concurrency, an embedded privileged helper, and a
Developer ID + notarised DMG as the shipping artefact.

---

## 0. What makes this project awkward

Read this before writing any YAML — four things here break the usual
"just run `xcodebuild test`" template.

| Constraint | Consequence for CI |
|---|---|
| `Cleat.xcodeproj` is generated by XcodeGen from `project.yml` | CI must run `xcodegen generate` first. The `.xcodeproj` should be gitignored, not committed. |
| There is no XCTest target — `Tests/QA/` are standalone `swiftc` programs | `xcodebuild test` has nothing to run. Tests are `Tests/QA/run.sh`. |
| Two of three harnesses need a **live NTFS volume** and a real process table | Only `MountPointGuardTests` can run on a hosted runner unconditionally. The rest need a fabricated NTFS disk image (§4) or a self-hosted Mac. |
| `Shared/BuildConfiguration.swift` cross-checks `DEVELOPMENT_TEAM` at runtime; the helper refuses XPC if it disagrees | The signing certificate used in CI **must** belong to team `CYY72W5P5F`, and CI should assert that rather than discover it after shipping. |

The helper itself (`SMAppService.daemon`) can never be meaningfully exercised in
CI: registering it requires root, a user approval in Login Items, and a real
NTFS device. Treat helper behaviour as a manual pre-release gate, not a CI job.

## 1. Prerequisites (one-time, done by you)

### 1.1 Put it in git

The project is not yet a repository.

```bash
git init
git add -A
git commit -m "Initial commit"
gh repo create cleat --private --source=. --push
```

Add generated build products to `.gitignore` before the first commit:

```
Cleat.xcodeproj/
```

`project.yml` is the source of truth; a committed `.xcodeproj` will drift and
produce spurious diffs on every Xcode launch.

### 1.2 Export the signing certificate

On your Mac, in Keychain Access, export the **Developer ID Application:
… (CYY72W5P5F)** identity *and its private key* as a `.p12` with a strong
password. Then:

```bash
base64 -i DeveloperID.p12 | pbcopy
```

### 1.3 Create an App Store Connect API key for notarytool

App Store Connect → Users and Access → Integrations → App Store Connect API →
generate a key with the **Developer** role. Download the `.p8` once (it is not
re-downloadable) and note the Key ID and Issuer ID.

An API key is strongly preferred over an Apple ID + app-specific password: it is
scoped, revocable, and does not carry 2FA state.

```bash
base64 -i AuthKey_XXXXXXXX.p8 | pbcopy
```

### 1.4 Repository secrets

`gh secret set NAME` for each:

| Secret | Contents |
|---|---|
| `BUILD_CERTIFICATE_BASE64` | base64 of the `.p12` from §1.2 |
| `P12_PASSWORD` | password you chose for that `.p12` |
| `KEYCHAIN_PASSWORD` | any random string; only used for the ephemeral CI keychain |
| `SIGN_IDENTITY` | e.g. `Developer ID Application: Your Name (CYY72W5P5F)` |
| `NOTARY_KEY_BASE64` | base64 of the `.p8` from §1.3 |
| `NOTARY_KEY_ID` | the Key ID |
| `NOTARY_ISSUER_ID` | the Issuer ID |

`DEVELOPMENT_TEAM` (`CYY72W5P5F`) is already public in
`Config/Signing.xcconfig` — it is not a secret and should not be one.

## 2. Pipeline shape

Three workflows, deliberately separate so a PR never touches signing material:

```
ci.yml          push + PR   →  generate, build Debug (ad-hoc), run volume-free QA
release.yml     tag v*      →  generate, build Release, sign, notarise, staple, GitHub Release
mount-qa.yml    manual/nightly → full QA against a fabricated NTFS volume
```

Pull requests from forks never receive secrets in GitHub Actions, so keeping the
signed path on tag-push only is both safer and less surprising.

## 3. `ci.yml` — the fast gate

```yaml
name: CI

on:
  push:
    branches: [main]
  pull_request:

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

jobs:
  build:
    runs-on: macos-15
    steps:
      - uses: actions/checkout@v4

      - name: Select Xcode
        run: sudo xcode-select -s /Applications/Xcode_26.app

      - name: Install XcodeGen
        run: brew install xcodegen

      - name: Generate project
        run: xcodegen generate

      - name: Build (Debug, ad-hoc signed)
        run: |
          set -o pipefail
          xcodebuild \
            -project Cleat.xcodeproj \
            -scheme Cleat \
            -configuration Debug \
            -destination 'platform=macOS,arch=arm64' \
            CODE_SIGNING_ALLOWED=NO \
            -derivedDataPath build/DerivedData \
            build | xcbeautify

      - name: QA harnesses (no volume required)
        run: Tests/QA/run.sh
```

Notes on the choices:

* **`macos-15` runner, arm64.** The deployment target is macOS 15 and the app is
  Apple-Silicon-only in practice. If you want to compile against the macOS 26
  SDK (for the FSKit backend paths), move to `macos-26` once you have confirmed
  it is available to your account, and keep `MACOSX_DEPLOYMENT_TARGET` at 15.
* **`CODE_SIGNING_ALLOWED=NO`** rather than the ad-hoc `-` from the xcconfig.
  Signing is not what this job is testing, and skipping it removes a whole class
  of keychain flakiness.
* **`xcbeautify`** is optional; drop the pipe if you would rather read raw logs.
  Install with `brew install xcbeautify` in the same step as XcodeGen.
* **`Tests/QA/run.sh` with no argument** compiles all three harnesses (so a
  compile break in any of them fails CI) and runs only the mount-point guard and
  sanitiser tests, which need no volume. This is exactly what the script already
  does — no changes required.

### Worth adding

Strict concurrency is already `complete` in `project.yml`. To stop warnings
accumulating, add `SWIFT_TREAT_WARNINGS_AS_ERRORS=YES` to the CI build
invocation only (not to `project.yml`, so local iteration stays comfortable).

SwiftLint is not currently in the project. If you add it, run it as a separate
non-blocking job first, then flip it to blocking once the baseline is clean.

## 4. `mount-qa.yml` — the tests that need a volume

This is the interesting one, and the reason most macOS projects stop at §3.

`Tests/QA/run.sh <bsdname>` needs an NTFS volume. macOS cannot create one —
there is no `newfs_ntfs`. But `mkntfs`, from the ntfsprogs shipped in the same
ntfs-3g source tree `Scripts/setup-dependencies.sh` already builds, can format a
raw disk image:

```bash
# Create a blank 256 MB image and attach it without mounting
hdiutil create -size 256m -layout GPTSPUD -type UDIF -fs '' -o /tmp/ntfstest
DEV=$(hdiutil attach -nomount /tmp/ntfstest.dmg | head -1 | awk '{print $1}')

# Format the first partition as NTFS
sudo /usr/local/bin/mkntfs --fast --label CLEATQA "${DEV}s1"

# Let DiskArbitration notice it, then hand the bsdname to the harness
diskutil list "$DEV"
Tests/QA/run.sh "$(basename "${DEV}s1")"
```

Two honest caveats:

1. **This is unverified on a GitHub-hosted runner.** FUSE-T installs a signed
   `.pkg` into `/usr/local` and, on macOS 26, an FSKit extension that must be
   enabled in System Settings — a UI action no headless runner can perform. On
   macOS 15 the NFSv4 loopback backend needs no approval and is the realistic
   target for automation; the FSKit path will need a real machine.
2. **The DiskArbitration harness unmounts the volume it is given.** Pointing it
   at anything other than a throwaway image is destructive. Guard the workflow
   so it can only ever run against a device it created in the same job.

Given that, structure it as `workflow_dispatch` + nightly `schedule`, on a
**self-hosted runner** (a Mac mini, or your own machine with the runner agent)
if you want the FSKit backend covered:

```yaml
name: Mount QA

on:
  workflow_dispatch:
  schedule:
    - cron: '0 7 * * *'

jobs:
  mount:
    runs-on: [self-hosted, macOS, ARM64]
    steps:
      - uses: actions/checkout@v4
      - name: Verify dependencies are present
        run: |
          test -f /usr/local/lib/libfuse-t.dylib || { echo "FUSE-T missing"; exit 1; }
          otool -L /usr/local/bin/ntfs-3g | grep -q libfuse-t || {
            echo "ntfs-3g is not linked against FUSE-T"; exit 1; }
      - name: Create throwaway NTFS volume
        id: vol
        run: |
          hdiutil create -size 256m -layout GPTSPUD -type UDIF -fs '' -o /tmp/ntfsqa
          DEV=$(hdiutil attach -nomount /tmp/ntfsqa.dmg | head -1 | awk '{print $1}')
          sudo /usr/local/bin/mkntfs --fast --label CLEATQA "${DEV}s1"
          echo "dev=$DEV" >> "$GITHUB_OUTPUT"
          echo "bsd=$(basename "${DEV}s1")" >> "$GITHUB_OUTPUT"
      - name: Run full QA
        run: Tests/QA/run.sh "${{ steps.vol.outputs.bsd }}"
      - name: Detach
        if: always()
        run: hdiutil detach "${{ steps.vol.outputs.dev }}" -force || true
```

The dependency-verification step is worth keeping even on a machine you set up
by hand: it catches exactly the `brew install ntfs-3g-mac` trap the README
describes, before the tests fail for a confusing reason.

## 5. `release.yml` — signed, notarised, published

### 5.1 Two small changes to `Scripts/build-dmg.sh`

The script is already environment-driven and needs no restructuring, but two
gaps matter for CI.

**(a) Version injection.** `MARKETING_VERSION` and `CURRENT_PROJECT_VERSION` are
hardcoded to `1.0` / `1` in `project.yml`. A release build should carry the tag.
Add pass-through to the `xcodebuild` invocation:

```bash
  ${MARKETING_VERSION:+MARKETING_VERSION="$MARKETING_VERSION"} \
  ${CURRENT_PROJECT_VERSION:+CURRENT_PROJECT_VERSION="$CURRENT_PROJECT_VERSION"} \
```

**(b) Notarisation credentials.** The script only supports
`--keychain-profile "$NOTARY_PROFILE"`. Rather than change it, have CI *create*
that profile from the API key — one command, and the script stays as-is:

```bash
xcrun notarytool store-credentials ci \
  --key AuthKey.p8 --key-id "$NOTARY_KEY_ID" --issuer "$NOTARY_ISSUER_ID" \
  --keychain "$KEYCHAIN_PATH"
```

Then `NOTARY_PROFILE=ci`.

### 5.2 The workflow

```yaml
name: Release

on:
  push:
    tags: ['v*']

permissions:
  contents: write   # needed to create the GitHub Release

jobs:
  release:
    runs-on: macos-15
    env:
      DEVELOPMENT_TEAM: CYY72W5P5F
    steps:
      - uses: actions/checkout@v4

      - run: sudo xcode-select -s /Applications/Xcode_26.app
      - run: brew install xcodegen
      - run: xcodegen generate

      - name: Import signing certificate
        env:
          BUILD_CERTIFICATE_BASE64: ${{ secrets.BUILD_CERTIFICATE_BASE64 }}
          P12_PASSWORD: ${{ secrets.P12_PASSWORD }}
          KEYCHAIN_PASSWORD: ${{ secrets.KEYCHAIN_PASSWORD }}
        run: |
          set -euo pipefail
          KEYCHAIN_PATH="$RUNNER_TEMP/signing.keychain-db"
          echo "KEYCHAIN_PATH=$KEYCHAIN_PATH" >> "$GITHUB_ENV"
          echo -n "$BUILD_CERTIFICATE_BASE64" | base64 --decode -o "$RUNNER_TEMP/cert.p12"
          security create-keychain -p "$KEYCHAIN_PASSWORD" "$KEYCHAIN_PATH"
          security set-keychain-settings -lut 21600 "$KEYCHAIN_PATH"
          security unlock-keychain -p "$KEYCHAIN_PASSWORD" "$KEYCHAIN_PATH"
          security import "$RUNNER_TEMP/cert.p12" -k "$KEYCHAIN_PATH" \
            -P "$P12_PASSWORD" -T /usr/bin/codesign -T /usr/bin/security
          security set-key-partition-list -S apple-tool:,apple:,codesign: \
            -s -k "$KEYCHAIN_PASSWORD" "$KEYCHAIN_PATH"
          security list-keychain -d user -s "$KEYCHAIN_PATH" login.keychain-db
          rm -f "$RUNNER_TEMP/cert.p12"

      - name: Assert the certificate's team matches Signing.xcconfig
        run: |
          set -euo pipefail
          XCCONFIG_TEAM=$(awk -F= '/^DEVELOPMENT_TEAM/{gsub(/ /,"",$2); print $2}' \
            Config/Signing.xcconfig)
          security find-identity -v -p codesigning "$KEYCHAIN_PATH" \
            | grep -q "($XCCONFIG_TEAM)" || {
              echo "Signing identity is not from team $XCCONFIG_TEAM."
              echo "The helper will refuse XPC connections from this build."
              exit 1; }
          echo "Team $XCCONFIG_TEAM confirmed."

      - name: Prepare notarytool credentials
        env:
          NOTARY_KEY_BASE64: ${{ secrets.NOTARY_KEY_BASE64 }}
          NOTARY_KEY_ID: ${{ secrets.NOTARY_KEY_ID }}
          NOTARY_ISSUER_ID: ${{ secrets.NOTARY_ISSUER_ID }}
        run: |
          set -euo pipefail
          echo -n "$NOTARY_KEY_BASE64" | base64 --decode -o "$RUNNER_TEMP/AuthKey.p8"
          xcrun notarytool store-credentials ci \
            --key "$RUNNER_TEMP/AuthKey.p8" \
            --key-id "$NOTARY_KEY_ID" \
            --issuer "$NOTARY_ISSUER_ID" \
            --keychain "$KEYCHAIN_PATH"
          rm -f "$RUNNER_TEMP/AuthKey.p8"

      - name: Build, sign, notarise, staple
        env:
          SIGN_IDENTITY: ${{ secrets.SIGN_IDENTITY }}
          NOTARY_PROFILE: ci
        run: |
          VERSION="${GITHUB_REF_NAME#v}"
          MARKETING_VERSION="$VERSION" \
          CURRENT_PROJECT_VERSION="$GITHUB_RUN_NUMBER" \
          Scripts/build-dmg.sh

      - name: Verify the shipped artefact
        run: |
          set -euo pipefail
          APP=build/DerivedData/Build/Products/Release/Cleat.app
          codesign --verify --deep --strict --verbose=2 "$APP"
          codesign -dv --verbose=4 "$APP" 2>&1 | grep 'TeamIdentifier=CYY72W5P5F'
          codesign -dv --verbose=4 "$APP/Contents/MacOS/CleatHelper" 2>&1 \
            | grep 'TeamIdentifier=CYY72W5P5F'
          spctl --assess --type execute --verbose=4 "$APP"
          xcrun stapler validate build/Cleat.dmg
          test -f "$APP/Contents/Library/LaunchDaemons/com.cleat.helper.plist"

      - uses: actions/upload-artifact@v4
        with:
          name: Cleat-dmg
          path: build/Cleat.dmg

      - name: Publish GitHub Release
        env:
          GH_TOKEN: ${{ github.token }}
        run: |
          gh release create "$GITHUB_REF_NAME" build/Cleat.dmg \
            --title "Cleat $GITHUB_REF_NAME" --generate-notes

      - name: Clean up keychain
        if: always()
        run: security delete-keychain "$KEYCHAIN_PATH" || true
```

The verification step is the part most pipelines omit and then regret. It
catches, before anything reaches a user:

* an unsigned or partially signed bundle (`--deep --strict`),
* a certificate from the wrong team — which would make the helper reject the app
  at runtime with a confusing XPC error,
* an unstapled DMG, which fails to open on a machine that is offline,
* a missing LaunchDaemon plist, which breaks `SMAppService` registration
  silently.

`spctl --assess` is the closest CI can get to "what Gatekeeper will do on the
user's Mac."

## 6. Release procedure

```bash
# 1. Everything green on main
# 2. Tag
git tag -a v1.1.0 -m "Cleat 1.1.0"
git push origin v1.1.0
# 3. Watch
gh run watch
```

Before tagging, run the manual gate that CI structurally cannot cover:

- [ ] `Scripts/setup-dependencies.sh` on a clean machine still succeeds
- [ ] Helper registers via Login Items on macOS 15 **and** macOS 26
- [ ] Real NTFS drive mounts read/write on both OS versions (FSKit and NFS backends)
- [ ] Eject / busy-volume handling behaves
- [ ] Downloaded DMG opens on a Mac that has never seen the app (Gatekeeper, offline)

`release.yml` also accepts `workflow_dispatch` with a tag input, so a failed
release can be retried from the Actions tab without re-tagging.

## 8. Things to reconsider later

* **Sparkle for in-app updates.** Direct DMG distribution means users have no
  update path today. Sparkle would add an appcast generation and EdDSA signing
  step to `release.yml`. Worth it once there is more than one release.
* **Caching.** Nothing here is slow enough to need it yet. If a self-hosted
  runner rebuilds ntfs-3g from source, cache `/usr/local/bin/ntfs-3g` keyed on
  the upstream commit rather than rebuilding nightly.
* **`SWIFT_TREAT_WARNINGS_AS_ERRORS`** in CI only, once the current warning count
  is zero.
* **Dependabot / `actions: pinned by SHA`.** For a private repo the risk is low;
  for a public one, pin third-party actions by commit SHA. Everything above uses
  first-party actions only, which is deliberate.
